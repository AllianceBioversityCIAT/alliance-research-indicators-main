# Proposal — CLARISA project auto-mapping (bilateral)

> **Headline:** CLARISA now publishes `external_code` — the AGRESSO code STAR already keys on — which is **the upstream join field that decision D-PI-8 recorded as non-existent**, and the reason the mapping was built manual one-by-one. That premise is dead, and the schema already has the seams (`source: AI_SUGGESTED | AI_AUTO`, `confidence_score`) waiting for it.
>
> **But two measurements block the obvious plan, and both were found by probing the live endpoints rather than reading the ticket:**
>
> 1. **Production does not have these fields at all.** All 13 new fields exist only in `clarisatest-back`. Prod returns 299 projects, `phase: null`, `source_center_acronym: null`, **zero** Alliance-2026 rows. This change cannot go live until CLARISA promotes the contract — a dependency on another team, not on us.
> 2. **Filtering on "has SPs" yields 5 projects, not ~380.** Of the 380 Alliance 2026 projects in test, only **5** carry a non-empty `project_mappings_array`. Either the test dataset is sparse or the filter is wrong. Building the matcher against 5 rows measures nothing.
>
> **Recommendation:** do **not** specify the auto-mapper yet. Specify a **two-stage** change whose first stage is a measurement harness that answers the one question nobody can answer today — *what fraction of STAR's AGRESSO contracts does `external_code` actually resolve?* — and gate the matcher's design on that number.

## 2. Intent

Replace the manual one-by-one AGRESSO↔CLARISA project mapping with an **evidence-graded automatic match** now that CLARISA publishes the join key, and surface each project's `description` in STAR.

---

## 3. Problem / Current Behavior

`bilateral_project_mapping` joins an AGRESSO contract to a CLARISA project **by hand**, one row at a time, through `/administration/center-admin/bilateral-mapping`. The entity's own comment states why:

> *"Admin-maintained … **no upstream join field exists per D-PI-8**."*

That is no longer true. Everything else follows from it.

| Today | Consequence |
| --- | --- |
| Every mapping is typed by an admin | Doesn't scale to 380 Alliance projects; the admin must already know which CLARISA project a contract is |
| `source` is always `MANUAL` | `AI_SUGGESTED` / `AI_AUTO` and `confidence_score` are **built and unused** — the schema anticipated this change |
| The client consumes 12 CLARISA fields | The 13 new ones — including `external_code`, `description`, `phase`, `source_center_acronym` — are not in `ClarisaProject` |
| Project description is not stored or shown | Nothing to display in STAR |

## 4. Measured reality (this is the part that changes the plan)

Probed **2026-08-14** against both environments. Every number below is counted from the raw payload, not inferred.

### 4.1 The two environments disagree about the contract

| | `clarisatest-back…/api/projects` | `api.clarisa.cgiar.org/api/projects` (prod) |
| --- | --- | --- |
| Projects | **1365** | **299** |
| `external_code`, `phase`, `source_center_acronym`, `external_source`, `source_status`, `last_synced_at` (+7 more) | present | **absent — the fields do not exist** |
| `phase` distribution | 2026 → 1066 · 2025 → 299 | all `null` |
| Alliance (CIAT+BIOVERSITY) & phase 2026 | **380** | **0** |

Prod's 299 rows correspond exactly to test's 299 `phase: 2025` rows. **Prod is the old dataset; test is ahead.** This directly answers the question raised mid-analysis — prod does *not* hold better data.

### 4.2 The Alliance 2026 slice

| Metric | Value | Reading |
| --- | --- | --- |
| CIAT | 273 | |
| BIOVERSITY | 107 | |
| **Alliance + phase 2026** | **380** | the population this change targets |
| …with non-empty `project_mappings_array` | **5** | ⚠️ see §12 OQ-2 |
| `external_code` populated | **380 / 380** | the join key is always present |
| `full_name` populated | 380 / 380 | fallback is always available |
| **`description` populated** | **74 / 380 (19%)** | ⚠️ the display feature is empty for 4 of 5 projects |
| `summary` populated | **0 / 380** | not an alternative |

### 4.3 `external_code` is not fuzzy — it is prefixed, and the prefix is the centre

This is the most useful finding, and it reframes the "sometimes the code doesn't match exactly" problem.

| Shape | n | Examples |
| --- | --- | --- |
| `B-A####` | 103 | `B-A1080`, `B-A1368` |
| `C-A####` | 98 | `C-A132`, `C-A171` |
| `C-D###` | 79 | `C-D182`, `C-D247` |
| `C-S###` | 45 | `C-S180`, `C-S209` |
| `C-O###` | 19 | `C-O139` |
| bare `A####` | 17 | `A1463`, `A1796` |
| bare `D###` / `S###` / `P###` | 17 | `D508`, `S240` |
| `C-F###`, `C-G###` | 2 | |

Cross-tabulated against the centre, the correlation is **exact, with no counter-examples**:

| Centre | `B-` | `C-` | no prefix |
| --- | --- | --- | --- |
| BIOVERSITY | **103** | 0 | 4 |
| CIAT | 0 | **243** | 30 |

So `B-`/`C-` is the source centre, and the remainder (`A511`, `D508`, `S240`) is the AGRESSO code STAR already stores. **The mismatch is a systematic, reversible normalization — not a fuzzy-matching problem.** A single strip-known-centre-prefix rule is expected to resolve the large majority; `full_name` comparison is then a *fallback for the residue*, not the primary strategy the brief assumed.

**And the normalization is safe:** stripping `^[BC]-` across all 380 projects produces **380 distinct codes — zero collisions**. It cannot merge two CLARISA projects onto one AGRESSO contract. (Closes OQ-3.)

### 4.4 `source_of_funding` — and a scope question the brief did not raise

Across all 1365 projects the value is inconsistent — `bilateral` (892), `Bilateral` (197), `window3` (172), `Window 3` (61), `BILATERAL - RESTRICTED` (16), `Bilateral - Restricted` (7) — so any filter on it must normalize (**Kaizen K-005**: a string used as a discriminator, unnormalized).

**Inside the Alliance 2026 slice it is clean, and that surfaces a real scope decision:**

| Value | n |
| --- | --- |
| `bilateral` | 342 |
| `window3` | **38** |

The brief's filter (`centre` + `phase` + has-mappings) does **not** mention funding source, so as written it would pull in **38 Window-3 projects** alongside the bilateral ones. Whether that is intended is OQ-5 — and it is not a detail: this module is named *bilateral* and drives the pool-funding tag.

## 5. Proposed Outcome

- STAR ingests the Alliance 2026 CLARISA projects and **proposes** mappings automatically, graded by how they were matched.
- An admin **confirms or rejects** proposals instead of typing them; manual creation stays available.
- Project `description` is stored and displayed where the project is shown.
- The match rule and its measured accuracy are recorded, so a future drop in upstream data quality is detectable rather than silent.

---

## 6. Scope

| In | Out |
| --- | --- |
| Extend `ClarisaProject` with the new upstream fields | Changing CLARISA itself |
| Alliance filter: `source_center_acronym ∈ {CIAT, BIOVERSITY}` **and** `phase = 2026` | Other centres; other phases |
| Normalize + match `external_code` → `agresso_contracts.agreement_id` | Free-text/AI semantic matching (see §10 Option C) |
| `full_name` comparison as a **fallback** for unresolved codes | Replacing exact matching with fuzzy matching |
| Persist `description`; surface it in STAR | Redesigning the project detail screen |
| Write mappings as `AI_SUGGESTED` with `confidence_score` | Auto-confirming without human review in v1 (see §11) |
| An admin review queue over proposals | Bulk edit of already-confirmed mappings |

---

## 7. Non-Goals

- Auto-**confirming** matches without review in the first release.
- Deleting or rewriting existing `MANUAL` mappings — they win over any proposal.
- Changing how `bilateral_project_mapping` drives the pool-funding tag (owned by the archived `mapping-drives-pool-funding-tag` spec).

## 10. Requirement Delta Preview

### ADDED

- Ingest Alliance 2026 CLARISA projects on a schedule (`tools/cron-jobs/`, per the server guide's integration rule).
- Normalize `external_code` by stripping a known centre prefix; match against `agresso_contracts.agreement_id`.
- Fallback comparison on `full_name` for codes that do not resolve.
- Persist project `description` and expose it.
- Persist match provenance (rule applied, confidence, matched-on value) so a match can be explained.
- Admin review queue: confirm / reject a proposed mapping.

### MODIFIED

- `ClarisaProject` gains the new upstream fields.
- `bilateral_project_mapping.source` starts taking `AI_SUGGESTED`; `confidence_score` becomes meaningful.
- The mapping list gains a source/confidence column and a "pending review" state.

### REMOVED

- Nothing. Manual creation is preserved as the escape hatch and as the winner on conflict.

## 11. Approach Options

| | Approach | Pros | Cons |
| --- | --- | --- | --- |
| **A** | **Deterministic normalizer + human review** — strip centre prefix, exact match, `full_name` fallback, write `AI_SUGGESTED`, admin confirms | Explainable and testable; every match has a stated rule; no model dependency; degrades to today's manual flow | Doesn't resolve genuinely ambiguous names without a human |
| **B** | Deterministic + **auto-confirm above a confidence threshold** | Least admin work | Threshold cannot be chosen honestly before §12 OQ-1 is measured; a wrong auto-confirm silently mis-attributes results to the wrong project |
| **C** | **AI/semantic matching** on `full_name` + `description` | Handles messy names | 81% of descriptions are empty (§4.2); unexplainable matches in an audit-bearing join; the deterministic rule (§4.3) likely covers the bulk anyway — this optimizes the residue first |

---

## 12. Recommended Approach

**Option A, delivered in two stages, with the second gated on a number we do not yet have.**

| Stage | Deliverable | Gate |
| --- | --- | --- |
| **S1 — Measure** | Extend the DTO, ingest the Alliance 2026 slice, and produce a **coverage report**: of STAR's live AGRESSO bilateral contracts, how many resolve by (a) exact `external_code`, (b) prefix-stripped code, (c) `full_name`, (d) not at all | Report reviewed with the user |
| **S2 — Automate** | Matcher, provenance, review queue, `description` surfacing — **designed against S1's actual distribution** | S1 numbers + CLARISA prod promotion (§13 R-1) |

**Why staged.** The brief asks which matching method to use. That question has a measurable answer and an unmeasurable guess, and §4.3 already moved it: the prefix rule is systematic, so `full_name` is probably a small-residue fallback rather than a co-primary strategy. But *probably* is not a design input. **S1 costs little and converts the central design decision from opinion into measurement** — and it is exactly the check that could not be run today, because the DEV database went unreachable mid-analysis (§13 OQ-1).

This also honours **Kaizen K-004**: a matcher whose accuracy is never measured against real contracts is a gate that cannot fail.

## 14. Success Criteria

- The Alliance 2026 slice is ingested and filtered by measured criteria, not assumed ones.
- The share of AGRESSO contracts resolved automatically is **published as a number**, and re-measurable later.
- Every automatic mapping states the rule that produced it and is reversible.
- No existing `MANUAL` mapping is altered.
- `description` is stored, and its 19% fill rate is handled explicitly in the UI rather than discovered by a user.
