## 1. Executive summary

A TIP publication is identified by its **handle** — the `public_link`, also stored as the `Handled` evidence. TIP returns the same handle once per year it was reported. Today STAR stores each handle-year as its **own live result with its own official code**, so a publication reported in 2023, 2025 and 2026 appears as up to three unrelated results and has no versions.

After this change, a handle is **one TIP result**:

- one **live row** — stable `result_id` and official code, carrying the data of the **highest year** TIP returned;
- one **version row per year** — `is_snapshot = 1`, same official code, carrying that year's data.

The sync creates or **updates in place** these rows; it never deletes and recreates them, so no `result_id` a link points at ever changes. Existing TIP data is converted once. STAR results and STAR versioning do not change.

## 2. Glossary

| Term | Meaning |
| --- | --- |
| Handle | The publication URL TIP sends as `link`; stored on the result as `public_link` and as the evidence row described `Handled` |
| Official code | `results.result_official_code`, generated by STAR (`newOfficialCode(TIP)` = last TIP code + 1); TIP sends no id |
| Live row | The TIP `results` row of a handle with `is_snapshot = 0`, `is_active = 1` |
| Version row | A TIP `results` row with `is_snapshot = 1`, `is_active = 1`, the handle's official code and one `report_year_id` |
| Highest saved year | The greatest year among the handle's saved version rows — earlier runs' and this run's; a year skipped as a duplicate is not saved |
| Run | One execution of the TIP sync (cron or `PATCH ipr-data/sync`) over a set of years |

## 5. Functional requirements

### R-TVR-001 — One TIP result per handle

The sync SHALL treat all TIP rows with the same handle as one result, sharing one official code.

#### Scenario: New handle

- GIVEN no TIP row has handle `H`
- WHEN a run brings `H` for 2025
- THEN a live row is created with a new TIP official code `C`
- AND a version row for 2025 is created with code `C`
- BUT it must NOT create a second official code for `H` in any later run

#### Scenario: Same handle, another year

- GIVEN `H` has live row code `C` (2025) and version 2025
- WHEN a run brings `H` for 2026
- THEN a version row for 2026 is created with code `C`
- AND IT MUST NOT create a new live row

#### Scenario: Equal codes across platforms

- GIVEN a STAR result with official code `C` exists
- WHEN the TIP handle's code is also `C`
- THEN both coexist; every TIP lookup in this spec filters by `platform_code = 'TIP'`

### R-TVR-002 — One version row per year, updated in place

For every year `Y` a run brings for handle `H` — except a year skipped as a cross-platform duplicate (R-TVR-003) — the sync SHALL write `Y`'s data to `H`'s version row for `Y`: create it when missing, update it in place when present.

#### Scenario: Version exists

- GIVEN `H` has version 2025 with `result_id` 500
- WHEN TIP changes the 2025 title and a run brings it
- THEN version 2025 shows the new title and keeps `result_id` 500
- BUT it must NOT delete and recreate the row

#### Scenario: First year seen also gets its version

- GIVEN `H` is new and a run brings only 2023
- THEN `H` has a live row and a version row for 2023

#### Scenario: Year TIP no longer returns

- GIVEN `H` has versions 2023 and 2025
- WHEN later runs bring only 2025
- THEN version 2023 is left unchanged (not deleted) — *default; owner to confirm at this gate*

### R-TVR-003 — The live row carries the highest saved year

The sync SHALL write year `Y`'s data to `H`'s live row only when `Y` is the highest year among `H`'s saved versions (this run's and earlier ones) **and not below the live row's current year**; otherwise the live row SHALL stay untouched. A year skipped as a cross-platform duplicate is not saved and so never becomes the live year.

#### Scenario: Highest year skipped as a duplicate

- GIVEN a run brings `H` for 2025 and 2026, and 2026 duplicates an AICCRA Capacity Sharing result
- THEN version 2025 is saved and the live row holds the 2025 data
- BUT 2026 must NOT be written to any TIP row

#### Scenario: Three years in one run

- GIVEN a run brings `H` for 2023, 2025 and 2026
- THEN `H` has versions 2023, 2025, 2026 and the live row holds the 2026 data with `report_year_id = 2026`

#### Scenario: Older year after a newer one

- GIVEN `H`'s live row holds 2026
- WHEN a run brings only 2025
- THEN only version 2025 changes
- BUT the live row must NOT change (data, year, `updated_at`)

#### Scenario: New highest year

- GIVEN `H`'s live row (`result_id` 400) holds 2026
- WHEN a run brings 2027
- THEN version 2027 is created and the live row holds the 2027 data
- AND IT MUST keep `result_id` 400 and code `C`

### R-TVR-004 — Pool Funding import lands on the rows written

The phase-1 Pool Funding import (`tip-kp-project-pool-funding` R-TIP-003) SHALL apply year `Y`'s mapping to `H`'s version row for `Y`, and also to the live row when R-TVR-003 wrote it.

#### Scenario: Two years, two mappings

- GIVEN 2025 maps `SP01` and 2026 maps `SP02`
- THEN version 2025 carries `SP01`, version 2026 and the live row carry `SP02`
- BUT it must NOT write one year's mapping onto another year's row

### R-TVR-005 — Staging is complete before processing

A run SHALL finish writing every staged publication before it reads staging back.

#### Scenario: Slow staging writes

- GIVEN staging writes resolve after the page loop ends
- WHEN the run reads staging
- THEN every publication TIP returned is read
- BUT a publication must NOT be skipped because its staging write had not finished

### R-TVR-006 — Existing TIP data is converted once

A one-off conversion SHALL bring existing TIP rows to the model of R-TVR-001..003.

- Handles with one live row: the row stays live (same `result_id`, same code). Its version row is created by the next full run (R-TVR-007).
- Handles with two live rows (63 in Dev): one stays live — the one with active links, otherwise the higher year; the other becomes the version row of its own year with the surviving code. Active links to the demoted row are re-pointed to the surviving live row.

#### Scenario: Two live rows, no links

- GIVEN `H` has live rows A (2025, code 21370) and B (2026, code 28469), neither linked
- WHEN the conversion runs
- THEN B stays live; A becomes version 2025 with code 28469 and keeps its `result_id`
- AND IT MUST record the before-values so the conversion can be reversed

#### Scenario: Linked older row

- GIVEN A (2025) has an active link and B (2026) has none
- WHEN the conversion runs
- THEN A stays live and B becomes version 2026 with A's code
- AND the next full run writes the 2026 data to A (R-TVR-003)

#### Scenario: Reverse

- WHEN the conversion is reverted
- THEN every converted row has its previous code, `is_snapshot` and `updated_at` back, and every re-pointed link points where it did before

### R-TVR-007 — Legacy TIP results

Every handle TIP returns SHALL get its version rows on the next run that covers its years (years skipped as cross-platform duplicates excepted) (a full run covers 2021 → current year). Handles TIP no longer returns keep their live row and get no version — *default; owner to confirm at this gate*.

#### Scenario: Legacy handle still in TIP

- GIVEN a TIP row created before this change for `H` 2024, and no version
- WHEN a full run brings `H` 2024
- THEN `H` has version 2024 and the same live row (`result_id` unchanged)

### R-TVR-008 — Re-running is idempotent

Running the sync twice over the same TIP data SHALL leave the same set of rows.

#### Scenario: Second run

- GIVEN a completed run
- WHEN the same run repeats with identical TIP data
- THEN the count of TIP rows, codes and versions per handle is unchanged
- BUT it must NOT create any row

## 6. Non-functional requirements

### NFR-TVR-001 — STAR unchanged

- **Category:** reliability
- **Target:** no change to any stored procedure, to STAR's snapshot paths, or to non-TIP calls of the shared section save; full server suite green
- **How verified:** body diff of touched shared code (TIP branch only) + `npm test`

### NFR-TVR-002 — No `result_id` changes

- **Category:** reliability / data integrity
- **Target:** the conversion and the sync change no existing `result_id`; links resolve to the same live row before and after
- **How verified:** conversion run on a Dev dump restored in the TEST container (owner preference, child 1), before/after id and link checksums

### NFR-TVR-003 — Reversible conversion

- **Category:** reliability
- **Target:** `down()` restores every converted value, `updated_at` included (child 1 lesson: UPDATEs keep `updated_at = updated_at`)
- **How verified:** up → down on the Dev dump; checksum of `results` TIP rows and `link_results` equal to the baseline

## 7. Defect classes and the gate for each

| Defect class | Gate |
| --- | --- |
| Lookup matches the wrong row (wrong key, missing `platform_code`, `is_snapshot`) | Integration spec on real MySQL (TEST container with a Dev dump) — mocked repositories cannot evaluate the generated SQL (KZ-001) |
| Live row overwritten by an older year | Same integration spec, scenario R-TVR-003 "Older year" |
| Rows duplicated on re-run | Integration spec runs the sync twice and compares counts |
| Pool Funding written to the wrong year's row | Integration spec, scenario R-TVR-004 |
| Staging read before it is written | Unit test with deferred (not synchronous) save promises |
| Conversion loses or misplaces data, or touches `updated_at` | Migration run on the Dev dump: before/after/after-down checksums |
| Versions not visible in the client's version selector | **No automated gate** — human check at the HITL pause on Dev |
| Compile errors hidden by the test runner | `npm run build` |

## 8. Risks

| ID | Risk | Mitigation |
| --- | --- | --- |
| RK-1 | STAR's `createSnapshot` lookups and `SP_delete_result_version` match code + year without platform. Once STAR reaches a code TIP uses, approving that STAR result could delete or collide with the TIP version of that number. | Out of scope (owner). Today STAR codes are 1–644 and TIP codes 2517+ in Dev. Recorded for a future spec. |
| RK-2 | The live row holds an older year than its newest version if a run is interrupted, or its live write fails, between versions and live | Narrowed by DD-3 (versions first, live once); healed by the next run that brings that year |
| RK-3 | Links counted 0 on demoted rows in Dev today may differ where the conversion is applied | The conversion counts and re-points at run time, and logs the count |
